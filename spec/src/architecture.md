# Architecture

## Requirements

| ID          | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| LC-ARCH-001 | The repository MUST publish one package named `@lapismd/lapis-community`; runtime code MUST live beneath `src` and MUST NOT be divided into nested workspace packages.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| LC-ARCH-002 | Signed Nostr events retrieved from configured relays MUST remain the registry source of truth. The package MUST NOT introduce an authoritative registry database or submission API.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| LC-ARCH-003 | `src/auth`, `src/nostr`, and `src/protocol` MUST own signer authentication, relay and Nostr-authenticated HTTP transport/querying, and deterministic event interpretation respectively. Fixture and materializer code MUST remain explicit supporting boundaries under `src`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| LC-ARCH-004 | The package MUST expose stable root, `auth`, `nostr`, `protocol`, `components`, `community`, and test-only `testing` entry points without leaking checkout-relative or workspace dependency paths into its publishable manifest.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| LC-ARCH-005 | Community presentation code and Storybook MUST consume Design Core through its published semantic-version range and public package exports. Direct icon dependencies MAY supply glyphs; framework-neutral emoji data/rendering and toast dependencies MAY provide package-owned NIP-30 and feedback behavior inside public Design Core chrome. Local source aliases, file dependencies, copied Design Core implementations, and Design Core forks are prohibited.                                                                                                                                                                                                                                                                                                                                                                                               |
| LC-ARCH-006 | The public `CommunityAppShell` MUST be the single application-frame composition for Inbox, channel, thread, and shell-backed component previews. Those surfaces MUST populate the public Design Core App Shell regions supplied by that frame instead of recreating header, viewport, sidebar, or joined-panel geometry in Storybook fixtures, and the complete examples MUST remain consolidated in the final App Shell catalog entry.                                                                                                                                                                                                                                                                                                                                                                                                                         |
| LC-ARCH-007 | Community sources, including the bounded registry adapter, MUST depend on a `CommunityRelayFactory` rather than constructing a concrete relay transport. The in-memory and WebSocket relay implementations MUST satisfy one observable contract so production, isolated Storybook scenarios, disposable Docker integration tests, and explicitly selected live-relay previews exercise the same materializer and controller. Sources MAY discover public NIP-29 rooms from authoritative relay metadata, but configured rooms MUST retain stable identity and discovery MUST NOT admit hidden groups or bypass the shared materializer. Live previews MUST NOT seed fixture events and MUST remain read-only unless a user-controlled NIP-07 signer is available.                                                                                               |
| LC-ARCH-008 | The public reactive `CommunityController` MUST consume a transport-independent `CommunityDataSource`, expose normalized state and stable actions, include the connected identity's projected profile metadata plus recent reply-participant identifiers and latest reply activity in normalized message models, and separate channel-root timelines from their complete thread projections. It MUST start live observation before its initial snapshot, buffer subscription replay until that snapshot is committed, batch subsequent live delivery, suppress duplicate IDs before reactive assignment, and cancel stale work when disposed or switched. Materialization MUST remain read-only for events held in reactive or immutable collections and MUST reuse boundary verification rather than rehashing accepted events. It MUST expose connection failures, support explicit reconnect, and own validated relay-URL changes through an injected local configuration store before rebuilding the active relay session. |
| LC-ARCH-009 | Identity signing and optional NIP-44 encryption MUST remain injected capabilities, while local and NIP-78 persistence MUST implement one `CommunityStateStore` boundary so anonymous reads and test runtimes do not depend on browser signers or remote storage.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| LC-ARCH-010 | `CommunityController` MUST accept either a static identity or a `CommunityIdentityConnector`, expose normalized authentication, member-directory, reply-target, navigation-preference, room-membership, lifecycle, and action-availability state, and reconnect its transport-independent sessions before retrying one protected action after interactive sign-in. Known permission denials MUST expose an accessible reason while uncertain relay permissions remain actionable. Room, member, reaction, read-state, custom-section, profile, status, and relay actions MUST remain controller-owned; non-portable terminal, huddle, agent, archive, edit, and feedback behaviors MUST be exposed only through typed optional host extensions.                                                                                                                 |

The static registry remains a deterministic projection. It can be rebuilt from
the event graph, configured trusted publisher and curator keys, and immutable
content-addressed manifests. The sibling `nostr-plugin-registry` repository owns
the Astro renderer, while the sibling `nostr-relay` repository owns relay
deployment and persistence.
