| LC-ARCH-007 | Community sources, including the bounded registry adapter, MUST depend on a `CommunityRelayFactory` rather than constructing a concrete relay transport. The reusable signed application scenario MUST include multi-author forum replies sufficient to exercise recent-participant and activity projection in the composed App Shell. | LC-ARCH-008 | The public reactive `CommunityController` MUST consume a transport-independent `CommunityDataSource`, expose normalized state and stable actions, preserve result kinds and stable room identities for search navigation, expose direct-message participant identifiers, profile metadata, unique reply participants, and latest reply activity in normalized models, and separate channel-root timelines from their complete thread projections. Forum replies MUST remain flat within the main content surface. Relative activity labels MUST derive from an explicit projection time so deterministic stories and tests do not depend on wall-clock time. It MUST start live observation before its initial snapshot, buffer subscription replay until that snapshot is committed, batch subsequent live delivery, suppress duplicate IDs before reactive assignment, and cancel stale work when disposed or switched. Materialization MUST remain read-only for events held in reactive or immutable collections and MUST reuse boundary verification rather than rehashing accepted events. It MUST expose connection failures, support explicit reconnect, and own validated relay-URL changes through an injected local configuration store before rebuilding the active relay session. |
| LC-ARCH-009 | Identity signing and optional NIP-44 encryption MUST remain injected capabilities, while local and NIP-78 persistence MUST implement one `CommunityStateStore` boundary so anonymous reads and test runtimes do not depend on browser signers or remote storage.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| LC-ARCH-010 | `CommunityController` MUST accept either a static identity or a `CommunityIdentityConnector`, allow an interactive identity connector to be selected after construction, expose normalized authentication, member-directory, reply-target, navigation-preference, room-membership, lifecycle, publish-availability, and action state, and reconnect its transport-independent sessions before retrying one protected action after interactive sign-in. Signing out MUST clear identity-bound projection state, reconnect anonymously, and retain public browsing. Known nonmembers MUST get a join prompt; role denials MUST expose a reason; queued participation MUST resume only after projected membership confirms the join; incomplete state remains relay-authoritative. Invalid commands and relay failures MUST produce structured, dismissible operation failures with the original relay reason and safe retryability instead of silently returning or discarding rejected promises. Room, member, reaction, read-state, custom-section, profile, status, and relay actions MUST remain controller-owned; non-portable terminal, huddle, agent, activity-log, archive, edit, feedback, wave, and follow behaviors MUST be exposed only through typed optional host extensions.      |
| LC-ARCH-011 | The package MUST expose one rebuildable `CommunityEventStore` contract with memory, IndexedDB, and lazily loaded Turso-WASM/OPFS implementations. The Turso adapter MUST consume the driver's Vite-aware public export so development and Storybook do not recursively transform its prebundled worker entry. Browser selection MUST prefer Turso only when OPFS, cross-origin isolation, shared memory, and Web Locks are available, then degrade to IndexedDB and memory without changing source or controller behavior. Stored event envelopes MUST remain verified, relay-derived, identity/scope partitioned, bounded by configurable retention, and disposable; the store MUST NOT become an authoritative application database. Persistent storage MUST contain only public NIP-29 events and encrypted NIP-17 gift wraps, never decrypted rumors or private NIP-29 plaintext.                                                                                                                                                                                                                                                                                                                                                                                                          |
| LC-ARCH-012 | `CommunityEventRuntime` MUST expose restoration, batched ingestion, projection, local search, and disposal through one pure runtime core shared by inline and dedicated-worker execution. The runtime MUST retain the canonical raw event collection, return only newly accepted event deltas after restoration, and return normalized workspace, Inbox, settings, and search projections without retransmitting the complete graph on each revision. Browser execution MUST recover one worker crash by restoring the disposable cache and MUST fall back to the inline runtime after a repeated failure while exposing degradation. Runtime responses MUST carry the controller generation and monotonic revision so stale work after reconnect or scope changes can be ignored. WebSocket transport, interactive NIP-07 signing, and Svelte state MUST remain on the main thread.                                                                                                                                                                                                                                                                                                                                                                                                           |
| LC-ARCH-013 | The public NIP-29 registry catalog source MUST open live release and curator subscriptions before querying configured relays, merge verified cached, queried, and buffered events without rollback, hydrate exact hash-verified manifests, and build the existing deterministic projection in browser memory. Its bounded snapshot store MUST persist only raw signed events, exact manifest bytes, synchronization metadata, and lazily requested verified resources in trust-fingerprinted memory or IndexedDB partitions. Any one relay completing the registry queries MAY mark the source fresh; partial failures MUST remain visible, failed hydration MUST retain the preceding revision, and cached state MUST remain non-authoritative and disposable. The source MUST use an injected reader signer or ephemeral in-memory signer for read-only NIP-42 authentication and MUST NOT prompt NIP-07 for catalog browsing.                                                                                                                                                                                                                                                                                                                                                               |

The static registry remains a deterministic projection. It can be rebuilt from
the event graph, configured trusted publisher and curator keys, and immutable
content-addressed manifests. The sibling `nostr-plugin-registry` repository owns
the Astro renderer, while the sibling `nostr-relay` repository owns relay
deployment and persistence.

The public `registry` entry point models that projection independently of
Svelte and relay transport. Its HTTP adapter validates static projection
documents and content references for compatible consumers. Its NIP-29 adapter
verifies relay events, manifests, and viewed resources before exposing an
ephemeral browser projection. The component entry point owns host-controlled
navigation, installation requests, source-health presentation, and optional
discussion composition. Projection-local image references are made absolute
only at the HTTP adapter boundary and must remain beneath the configured
registry root; relay-backed media is exposed only through verified Blob data.
