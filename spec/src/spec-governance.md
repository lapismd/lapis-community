# Specification Governance

## Requirements

| ID          | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| LC-SPEC-001 | `spec/src` MUST remain the canonical standalone package specification and MUST build with mdBook through `@lapismd/spec-validator`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| LC-SPEC-002 | Protected package manifests, runtime and development dependencies, source, Storybook, Docker, script, and repository-policy changes MUST update an owning canonical chapter in the same Jujutsu change; dependency additions MUST identify the package-owned behavior they support.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| LC-SPEC-003 | Every normative requirement ID MUST be unique and MUST have exactly one verification row containing concrete evidence.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| LC-SPEC-004 | Repository validation MUST include formatting, specification, Svelte and TypeScript checks, unit tests, the memory relay contract, opt-in Docker relay conformance, Storybook interaction and accessibility tests, a static Storybook build, package build, and publish-manifest validation. Storybook MUST use the shared Design Core catalog layout, package-owned theme and relay-backend controls, isolated default scenarios, an explicitly labelled non-seeding live registry relay option initialized to the local registry relay unless overridden, and explicit section ordering that leaves composed examples after focused component sections. Live connection failures and locally persisted endpoint changes MUST remain observable in the production composition. Shell-backed stories MUST opt into the generic full-viewport canvas marker while leaving application-frame styling in the production component. Local Storybook MUST send COOP `same-origin` and COEP `credentialless` so the Turso/OPFS worker lane can run without requiring credentials for external avatars or emoji; hosts without isolation MUST continue through IndexedDB. |
| LC-SPEC-005 | Repository guidance MUST require production-component Storybook scenarios, consumer-usable documentation, real interaction and accessibility evidence, human-gated visual baselines, and checkout-local Storybook processes and ports. Retained full-shell stories MUST exercise their primary controls; obsolete shell variants MUST not remain as misleading catalog examples.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

`@lapismd/spec-validator` is development-only governance tooling. Published
runtime dependencies use ordinary npm semantic-version ranges and never local
workspace, file, or link dependencies. The package-owned rebuildable event
cache uses `idb` for its durable fallback and lazily loads
`@tursodatabase/database-wasm` only when the host meets the OPFS isolation
requirements.

Relay conformance tests live under the test-only package entry point. They run
in memory by default and may target the disposable Docker relay without adding
environment-specific branches to production controller or materializer code.
